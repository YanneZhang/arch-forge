# <span style="color:rgb(0, 112, 192)">1 缓存概述</span>

1. 浏览器中、网关、负载均衡、应用服务器、数据库
2. 文件、数据、页面均可缓存
## <span style="color:rgb(0, 112, 192)">1.1 分布式缓存</span>
### <span style="color:rgb(0, 112, 192)">1.1.1 分流</span>
1. 通过负载均衡将请求分散，减少每个系统处理的用户请求数，
### <span style="color:rgb(0, 112, 192)">1.1.2 并发</span>
1. 通过代码的优化，多线程，提升单个系统处理任务的能力
### <span style="color:rgb(0, 112, 192)">1.1.3 导流</span>
1. 对较慢的查询的数据，引导或存储到较快的介质中
2. 操作耗时，引导到缓存中
## <span style="color:rgb(0, 112, 192)">1.2 缓存原理</span>
1. 用空间换时间的，单位时间内能处理的数据多一些
2. 将对访问频次高的数据，存储在读取速度快的介质中
3. 客户端和服务器端都有缓存的介质
4. 通过大量计算得出结果的数据，在第一次访问时或不定时计算好后缓存到介质中
5. 缓存读的次数大于写的次数
6. redis，memcache，guava，localcache

# <span style="color:rgb(0, 112, 192)">3 缓存key的设计</span>
1. 根据业务生成
2. 快速生成
	- 生成key的时间要快速，影响的因素是生成的算法
	- 检索key要快，影响的因素与物理位置有关、进行key的比较
	- hash算法，公认的生成和检索都快的算法，正向快，不可逆向，原始数据有一点变动，得出的结果差别很大，避免冲突，
	- md4，md5，sha-0，sha-1均不安全了
	- SHA-2: SHA-224(输出224位)\SHA-256(输出256位，2的256次方相当于10的77次方)\SHA-384(输出384位)\SHA-512(输出512位)均是安全的，避免冲突、产生重复的数据，算法的位数越大，生成的时间越高
3. 防止重复
# <span style="color:rgb(0, 112, 192)">4 缓存值的设计</span>
1. 序列化数据，对象的序列化的串，读出后需要反序列化
	- 可以存音频，视频，图片等待
	- 写入和读取时，需要花费序列化和反序列化时间
	- 二进制，便于存储
2. 对象数据
	- 数据转换方面，效率高
	- 有可能存入的是对象的引用
	- A业务在改动对象数据时，B在读，所以B有可能读到污染的数据
# <span style="color:rgb(0, 112, 192)">5 缓存风险</span>
1. 频繁修改的数据，数据写入缓存后，应用还来不及读取，就被人修改了，读写比在2：1以上，这样的缓存才有意义
2. 没有热点的访问，不遵循二八定律，
3. 数据不一致与脏读，缓存有失效时间，应用要容忍一段时间的缓存和数据不一致
4. 缓存可用性，缓存雪崩，缓存不可用时，数据库不能承受压力，使用缓存热备提升缓存可用性
5. 对缓存进行业务区分，如A缓存是订单，B缓存是用户，C缓存是积分等等，也可以提升缓存可用性
6. 缓存预热问题，缓存启动时，把一些数据加在到缓存中
7. 缓存击穿(缓存没有，数据库有)，缓存穿透(缓存没有，数据库也没有)，不恰当的业务或者攻击，频繁的请求数据

## <span style="color:rgb(0, 112, 192)">6.1 被动更新(时效性缓存)</span>

1. 在一定时间内，清理过期缓存，等待调用方发起调用后，再从数据提供方获取数据，在一段时间内放弃了缓存内的数据，保持了最终一致性
2. 在有效期内，无论数据提供方怎样变化，缓存都不变
3. 缓存设置有效期，读多写少
4. 适用场景：地区数据，规则类数据，商品关注人数

![[2a8a23f6-4055-4c61-8c8c-402e7b26b8d2.png]]
## <span style="color:rgb(0, 112, 192)">6.2. 主动更新</span>
1. 数据提供方的数据有变化，主动更新缓存，数据提供方更新。
2. 修改缓存
3. 删除缓存，查询时发现缓存没有数据，读同时放入缓存

## <span style="color:rgb(0, 112, 192)">6.3 数据库和缓存更新的组合方式</span>
1.  先更新缓存，再更新数据库 <span style="color:rgb(255, 0, 0)">（X，不可取）</span>
	如果更新缓存成功，更新数据库失败，所以每次查询都是错误的数据，造成数据不一致风险大
2.  先更新数据库，再更新缓存<span style="color:rgb(255, 0, 0)">（X，不可取）</span>
	在多线程情况下，A被阻塞，B顺利执行，B把数值变成2，A继续操作时把数值变成1，
	线程安全方式，分布式情况
![[Pasted image 20260526111546.png]]
3. 先删除缓存，再更新数据库
* 一个写线程去写数据，写之前先删缓存，这时另一个线程去读缓存，发现缓存没数据，就去数据提供方读并更新缓存，这时缓存是旧值了，因为写比读慢，然后写才去更新数据提供方，这样数据提供方和缓存的数据就不一致了；
* 另一个方案是延时双删，先删除缓存再更新数据库，然后休眠1s，再次删除缓存，此时再读时从数据提供方更新到缓存中了，此时数据是最终一致了，但是休眠1s时，大量读的进程读的就是错误的数据
* 休眠时间用读的时间+200~300ms即可
* 如果数据库采取了读写分离，写新库，读旧库，还是采用双删策略，休眠时间改为主从同步时间+几百毫秒
* 延时双删影响吞吐量，休眠时用户还在等待响应，吞吐量就会降低，
	* 1.为提升系统吞吐量，将缓存删除操作异步化，通过独立线程执行，使写请求无需等待缓存删除完成即可返回，减少用户响应时间。
	* 2.异步删除缓存策略中，若第二次删除失败，需设计重试机制，确保缓存最终一致性，避免数据不一致问题，假设单库情况
		* 引入消息队列机制，可将失败的key放入消息队列，利用重发机制持续尝试删除，直至成功，提高删除操作的可靠性和效率
		* 更新数据库时，产生binlog日志，通过Camel订阅bin log，提取操作的key，再删除，删除失败时，把key放到消息队列中，
		* 增加重试次数、设置合理的重试间隔时间，以及引入分布式锁等手段，确保在高并发场景下缓存删除操作
![[18c511c2-636b-46c0-b824-fbcb913c73be.png]]
4. 先更新数据库，再删除缓存《书名：CacheAside》应用非常广的方案
	1. 失效：应用先从缓存中取数据，没取到，说明缓存失效了，再读数据库并更新缓存
	2. 命中：从缓存中取数据，取到了
	3. 更新：先把数据库更新，更新完，再让缓存失效，Facebook也用这种策略
	4. 风险：A线程查询缓存失效，B线程更新数据库并删除缓存，然后A更新缓存了
		* 1 读操作的时候，缓存中无数据。  
		* 2 读操作的时候，有一个写在进行。  
		* 3 读操作在数据提供方中读取数据的时长，大于写操作，这个概率就很低。  
		* 4 读写并发的时候，读取到旧值。
		* 5 解决这些问题，给缓存设置时间段，做异步延时删除，每删除一次缓存，隔一段时间后再删除一次缓存
![[024c9440-c270-4e0c-91dd-41bf409a06f0.png]]

 1. Read/Write Through

	 * 另一部分数据是业务执行过程中产生的数据

	 * CacheAside方案中，缓存是辅助作用，缓存不存在也可以

# <span style="color:rgb(0, 112, 192)">7 缓存清理机制</span>
1. 提升命中率，增加缓存收益，增大缓存存储空间
2. 需时刻记住：何时清理，用什么条件清理，清理什么样的数据
3. 清理频率：按照时间来清理，一周，一月，一年等等，按照空间来清理，磁盘达到百分之多少时清理，
4. 清理的数据：清理在未来一段时间内不被访问，保留未来时间内频繁访问的数据，一条数据最近被访问，在接下来时间也会被访问，最近写入的数据
5. 淘汰算法，
6. 时效制清理机制，每条数据都有失效时间，自带过期时间
	* 应用程序再开一个线程轮询扫描所有数据，发现哪一条数据超过过期时间，就清理掉
	* 缓存自动删除，缓存内部也是轮询扫描
7. 数目阈值式清理机制
	* 根据缓存空间大小和缓存数据量大小决定，由系统业务决定
	* 先进先出FIFO，java中用linkedhashmap
	* LRU latest recently  used，最近最少使用，长久未访问的数据，有一个链表，每访问一次就放到链表头部，最后清理链表尾部的数据，java中用linkedhashmap，直接存储键值对，有顺序的，插入顺序实现FIFO，访问顺序实现LRU
8. 系统空间充足，缓存应占用大空间，提高命中率，系统空间不足时，将缓存空间让出来给到更为核心的模块，也就是说需要弹性控制空间，类似内存回收
9. JVM中引用
	* 强引用：不释放
	* 软引用：空间紧张时才释放
	* 弱引用：检测到就释放
	* 虚引用：检测到就释放
10. 常访问用强引用，不常访问用软引用
11. LRU+软引用方式
12. 缓存清理和更新机制同时设计
# <span style="color:rgb(0, 112, 192)">8 缓存的风险</span>
系统环节越多，越容易出错，分析缓存风险从更新和删除这两方面考虑
## <span style="color:rgb(0, 112, 192)">8.1 缓存击穿</span>
1. 存在高频率数据，数据失效了，访问到数据提供方上
2. 被高频率访问，大概率不会被清空
3. 有时效的数据，到期时，突然大量访问
4. FIFO，刚要删除，突然大量访问
5. 软引用，会有击穿的可能性
6. cache-aside，会有击穿的可能性
7. 避免击穿，使用LRU，read/wirte-through，write behind
## <span style="color:rgb(0, 112, 192)">8.2 缓存穿透</span>
1. 缓存和数据提供方都没有的数据
2. 在数据提供方返回空值时，也放到缓存中，下次访问时，避免访问到数据提供方中
3. 

## <span style="color:rgb(0, 112, 192)">8.3 缓存雪崩</span>
1. 大量缓存突然失效，都访问到数据提供方上
2. 用数据阈值方式，不会出现这个情况
3. 用时效式清理机制，在某个时间节点，大量缓存都到期了，会发生雪崩，解决方案：设置时效时间再额外加随机值
4. 软引用式清理，空间紧张时，会发生雪崩，解决方案：LRU+软引用

## <span style="color:rgb(0, 112, 192)">8.4 缓存预热</span> 
1. 提前把数据加载到缓存中
2. 针对read/wirte-through，write behind，这两种方式，需要对数据进行预加载
3. 时效式导致重复预热问题
4. 识别热点数据，提前放到缓存中
# <span style="color:rgb(0, 112, 192)">9 缓存的位置</span>
## <span style="color:rgb(0, 112, 192)">9.1 位置</span>
1. cpu计算速度快，避免cpu花时间等内存的数据，所以出现了缓存
2. 缓存容量比内存小，比内存速度快，解决cpu和内存速率不同的问题
3. CPU分三级缓存，1级缓存速度快，容量小，L1D，L1I
4. cache miss 缓存未命中，去数据提供方获取
5. 缓存位置
	5.1 客户端位置：穿戴设备，app等，胖客户端(某个客户端有，其他客户端不需要有)，存储位置有web端的localstorage，sessionstorage，applicationstorage等等
	5.2 静态缓存：静态页面，图，餐厅评分，地区数据，每个用户看到都相同，与用户个体无关的数据，CMS系统，放置在CDN或磁盘中
	5.3 服务端缓存和数据库缓存：服务缓存=>网关，负载均衡，具体的服务等；数据库中增加冗余数据、中间表、历史表、msyql提供了缓存,buffer pool缓存sql等的执行结果，数据库中的查询缓存等，查询语句的大小写需要系统内统一
	5.4 根据复用的时间段，选取缓存的数据，	缓存的位置
# <span style="color:rgb(0, 112, 192)">10 写缓存</span> 
1. 数据处理方，就是对数据进行加工的
2. 加了缓存后，增加了缓存处理时间，数据同步到缓存的时间
3. 增加写缓存后，减少了缓存处理时间，数据同步到缓存的时间，写缓存的时间小于数据处理方处理的时间，写缓存的收益就有了
4. 写缓存只能减少响应时间，增加了系统总处理时间，增加系统复杂度，增加缓存和数据提供方数据不一致的风险
5. 写缓存在调用方和数据处理方之间
6. redis、mq做写缓存，发布和消费
