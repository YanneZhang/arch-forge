# <span style="color:rgb(0, 112, 192)">1 代码优化</span> 
## <span style="color:rgb(0, 112, 192)">1.1 多线程</span> 
1. IO阻塞
	1. 磁盘IO和网络IO，都需要等待
2. 多CPU
3. 最大限度使用CPU，thread、runnable、线程池
4. 解决线程安全的手段：
	1. 将对象设计成无状态对象，对象无成员变量，成员变量也是无状态的，如servelet
	2. 使用局部对象，方法内部创建的对象
	3. 并发资源用锁，访问的资源是否其他线程是否访问，考虑锁的粒度
## <span style="color:rgb(0, 112, 192)">1.2 资源复用</span>
1. 单例模式，spring就是单例，减少对象创建，常量存储的类，工具类
2. 对象池，复用对象的实例，减少对象消耗
# <span style="color:rgb(0, 112, 192)">2 存储设计</span> 
1. 读写分离，分散访问压力，没有分库、分表
	1. 主从集群（应对复制延迟带来的复杂度，以mysql延迟至少1s以上）
		1. 写操作后的读操作指令发给主去读，和业务绑定有点强
		2. 关键业务操作只限主库
		3. 读从机失败后，再次读主机
	2. 主备集群（备机不提供访问）
2. 分库、分表，分散存储压力
	1. 数据量大，索引量也很大，备份和恢复耗费时间长，所以需要分库、分表
	2. 从业务上进行区分
	3. 应对高并发场景，读多写少（增加从库，加缓存，不需分库、分表），还是读少写多（写入的qps达到瓶颈时，需要分库、分表），
	4. 非核心业务有问题时，会影响核心业务，所以需要分库、分表
	5. 不破坏单表数据条数、表结构
	6. 破坏表数据、表结构
	7. 水平拆分
	8. 垂直拆分
	9. 让查询操作尽量不要跨表
	10. 分库分表前考虑的事情，路由（找到数据）、拼接（操作数据）
3. 分库分表方法
	1. 范围，根据单条记录大小，业务对表的操作
	2. hash运算
4. 出现问题
	1. 如每个表的id是自增的，每个表都有相同id，此时需要有个id生成服务，
		1. 分布式id（全局唯一，高性能，高可用，好接入）
		2. uuid 网卡+时间+随机数，生成简单，性能好，没有高可用风险
		3. 可以用数据库自增id，用不同的步长生成不同的数据
		4. 批量id
		5. redis生成id
		6. 雪花算法
	2. join问题：尽量不要三张表以上关联，在代码中进行处理
	3. 事务问题：分布式事务
	4. 成本问题：原来一个库解决，现在多个库，资金、人力、代码复杂度，非必要不要添加
